### On Quarkus, an engine on a named datasource and the application's datasource may not both be without XA

Built by story 2046 on 2026-10-30.

On Quarkus, an engine on a named datasource joins the same JTA transaction as the application's
datasource. Its job loads and saves the workflow aggregate there, and the platform's outbox and
delivery log write there. Narayana takes in only one datasource without XA per transaction. The
second one fails with `Exception in association of connection to existing transaction`. Then the
task handler has run, but the engine's job rolls back (`ENGINE-11001`), and the job is tried again.
A start through the outbox fails the same way and is repeated without end.

Nothing shows this before the first task runs. So the boot checks it. The engine producer stops the
boot if all of this holds for a `camunda7` adapter id:

- the id runs on a named datasource (`vanillabp.adapters.<id>.data-source-name`, not `default`),
- that datasource has `quarkus.datasource.<name>.jdbc.transactions: enabled`, which is Quarkus'
  default,
- the application has a second datasource with `enabled` as well. That is the default datasource
  if there is one, and the datasource of Hibernate ORM (`quarkus.hibernate-orm.datasource`).

The message names the adapter id, both datasources and both keys. Making either side an XA
datasource is enough, because Narayana takes one datasource without XA next to XA datasources.
`transactions: disabled` is not checked. Such a datasource never joins a transaction, so it does
not cause this failure.

The boot stops and does not warn. A configuration which the check stops does not work today: every
task of that engine is rolled back after its handler ran. A configuration without a second
datasource still boots, for example an application whose only datasource is the engine's and whose
outbox is on MongoDB. An engine on the default datasource is not checked, because its transaction
has one datasource only.

Spring Boot is not affected. There the engine on its own datasource commits through a transaction
manager of its own, bound to that datasource.
