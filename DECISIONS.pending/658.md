# Compensation is reported although this engine starts the handlers one after the other

The core warns about a BPMN process which can hold more than one token while its workflow
aggregate has no version attribute, and compensation now belongs on that list: a throw event
which compensates two finished activities starts both handlers, and each handler is an ordinary
workflow task writing the same aggregate. This adapter reads its model for it and reports
`CompensationSpec(throwEventId, handlerIds)` for every throw event which starts more than one
handler.

What this engine really does was measured first, because a message has to say what holds.

## What was measured

On 2026-09-27, against the embedded engine of Camunda 7.24 on H2, with the model
`api/compensation-facts.bpmn` and the test `Camunda7CompensationTokensTest`. Two service tasks,
a compensation boundary event and a handler on each, one compensation throw event.

- The engine creates both compensating executions before it signals any of them. While the first
  handler runs, its parent execution has two children, so the workflow holds two tokens.
- It signals them one at a time, and the second handler starts once the first one returned. No
  two handlers were inside their delegate at the same moment, in any of the three setups
  measured.
- The order is not stable. The engine sorts the compensation subscriptions by their creation
  time, which is a `java.util.Date`, and `Collections.sort` is stable, so two activities whose
  subscriptions were created in the same millisecond are compensated in the order they ran in
  rather than in the reverse one. Both orders were observed in the same test within an hour.
  This is not a deviation we report, it is what the wiki already says: VanillaBP promises
  nothing about the order of compensation.
- The adapter sets `asyncBefore` on every service task, and the flag IS set on the handlers. The
  engine ignores it there: it starts a compensation handler with `executeActivity`, outside the
  normal flow, where no job is created. One job existed at a time, and the whole compensation ran
  in the transaction of the throw event.
- With the job executor running, both handlers ran on one thread.

So two compensation handlers made of service tasks never write the aggregate at the same moment
on this engine.

## Why the report is made anyway

The check asks whether the process can hold more than one token, not whether two threads are
inside a handler. Both compensating executions exist from the moment the throw event runs. It is
the same answer a forking parallel gateway gets here, where the exclusive jobs of one workflow
are serialised by the job executor as well and the adapter reports the gateway all the same.

And a handler which WAITS keeps its token while the next handler is started. Two compensation
handlers drawn as user tasks are open at the same time, and the application completes them in two
transactions which may overlap. Leaving compensation out because the everyday case is a service
task would make the check quiet about the case which actually loses a write.

The wording of the core's message follows the measurement: it says the handlers can be open at
the same time, not that they run in parallel.
